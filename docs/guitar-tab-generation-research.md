# YouTube 楽曲からギター TAB 譜を生成する Web アプリ：技術調査と構成案

調査日：2026-09-28

## 結論

精度を優先するなら、**音源取得 → ギター音の分離 → ギター用の音符推定 → 弦・フレットの割当 → TAB 譜表示 → ユーザー修正**を独立した工程にする。音高が合っていても、同じ音を弾ける弦とフレットは複数あるため、MIDI をそのまま TAB 譜として扱えない。[tuttut の解説](https://github.com/natecdr/tuttut)

最初の実装候補は **Demucs `htdemucs_6s` + ギター専用 Audio-to-MIDI モデル + 独自の運指最適化 + alphaTab**。Basic Pitch を比較用の基準モデルとして並走させる。曲全体を一度に処理する前に、短い区間のリードギターまたは単一のギターパートで精度を検証する。この組合せの優位性は未検証であり、下記の評価計画で確かめる。

## 主要な候補

| 工程 | 候補 | 採用上の利点 | 注意点・位置付け |
| --- | --- | --- | --- |
| 音声の前処理 | [FFmpeg](https://ffmpeg.org/documentation.html) | 入力形式の変換、モノラル化、サンプルレート調整、短い区間への切り出し | 音符の推定は行わない |
| ギター音の分離 | [Demucs `htdemucs_6s`](https://github.com/facebookresearch/demucs) | 6 ステムに `guitar` が含まれる。まず試すモデル | 分離漏れや他楽器の混入が後段の誤認識につながる。推論は重い |
| 分離モデルの比較 | [audio-separator](https://github.com/nomadkaraoke/python-audio-separator) | 複数の分離モデルを同じ処理系で試せる | モデルごとに出力対象、品質、ライセンスを確認する。初期実装では必須にしない |
| 音符推定・第一候補 | [GAPS のギター転写研究](https://arxiv.org/abs/2408.08653) と [ギターモデルを利用できる推論実装](https://github.com/xavriley/hf_midi_transcription) | ギター音で学習したモデルを比較対象にできる | GAPS の研究対象は主にソロのクラシックギター。混合音源から分離したロック音源への性能は要検証。推論実装のギターモデルが多声和音にどこまで対応するかも検証する |
| 音符推定・基準 | [Spotify Basic Pitch](https://github.com/spotify/basic-pitch) | 導入しやすく、多声音・ピッチベンドに対応。MIDI とノートイベントを出力できる | 公式説明では単一楽器の録音に最も適する。弦・フレットは出力しない |
| 音符推定・比較候補 | [Magenta MT3](https://github.com/magenta/mt3) | 複数楽器の転写を目的とする研究モデル | 構築が複雑。ギターの弦・フレットは推定しない。初期構成には入れず比較実験に回す |
| 直接 TAB 推定・比較候補 | [TabCNN 実装](https://github.com/simon-minami/tabcnn) | 音声からギターの弦・フレットを直接推定する方向を試せる | 学習済み重みと対象音源への適合性を確認する。曲全体にそのまま使えるとは限らない |
| 運指割当 | [tuttut](https://github.com/natecdr/tuttut) を参考にした最適化 | MIDI から弦・フレットを決める問題の実装例 | 楽曲に合う運指、同時発音、ポジション移動、チューニングを考慮した独自処理が必要になりそう |
| TAB 表示 | [alphaTab](https://docs.alphatab.net/) | ブラウザーで TAB、五線譜、再生カーソルなどを表示。MusicXML、Guitar Pro、alphaTex を読み込める | 表示ライブラリであり、音声から TAB を推定する機能ではない |

**研究段階の注目候補：** [TART（2026 年の論文）](https://arxiv.org/abs/2609.11904) は音声から MIDI、奏法、弦・フレットを順に推定する構成を提示している。論文が報告する end-to-end TAB F1 は評価した 4 データセットの平均で 54.08%。これは特定の評価条件下の数値で、一般の YouTube 楽曲での精度を保証しない。公開済みの再利用可能なコード・重みを確認できるまでは、設計の参考とする。

## 推奨アーキテクチャ

```text
Web UI（React / TypeScript、alphaTab）
  ├─ YouTube URL の入力、対象区間・ギターパート・チューニングの指定
  ├─ 進捗、分離音の試聴、TAB の表示と修正
  └─ MusicXML / MIDI の書き出し
             │
             ▼
API（Python / FastAPI）── ジョブキュー（Redis + RQ など）
             │
             ▼
処理ワーカー（Python / PyTorch、GPU があれば使用）
  1. 利用可能な音源を受け取り、FFmpeg で正規化・区間切り出し
  2. Demucs でギターを分離。分離前後の音を保存して比較可能にする
  3. ギター専用モデルと Basic Pitch でノート候補を作る
  4. ノートの開始・終了、重複、誤検出を補正する
  5. 指定チューニングとフレット数の下で弦・フレットを割り当てる
  6. 拍・小節・音価に整え、MusicXML へ変換する
             │
             ▼
保存領域（音声中間ファイル、ノートイベント、TAB 編集結果、ジョブ状態）
```

**内部データ形式：** MIDI だけを正本にせず、各音の `pitch`、`onset_seconds`、`offset_seconds`、`confidence`、`string`、`fret`、`technique` と推定元モデルを保持する。弦・フレットを修正しても音符推定をやり直さずに済む。最終的に [MusicXML の TAB 用 `string` / `fret` 情報](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/technical/)を含むファイルを作り、alphaTab に渡す。MIDI も任意で書き出せるようにする。

**運指の決定：** まず各音の候補位置をチューニングから列挙し、同じ弦で同時に 2 音を鳴らさない、届かないフレット間隔を避ける、直前からの手の移動を抑える、といった制約で小節またはフレーズ単位に最適化する。開放弦やコードフォームの好みは重みとして調整可能にする。ドロップ D などの変則チューニングはユーザー指定から始め、自動推定は後回しにする。

**AI の使い方：** 主な音符・運指の推定は音声モデルと制約付き最適化で行う。生成 AI を加えるなら、候補の説明や修正提案に限定し、推定した音高と演奏可能性の制約を通った結果だけを譜面に反映する。音を聴かずに TAB 文字列を生成する方式では誤りを検証しにくい。

## YouTube URL の扱い

URL の入力と音源の取得は別問題。[yt-dlp](https://github.com/yt-dlp/yt-dlp) は技術的には音声を取得できるが、[YouTube の利用規約](https://www.youtube.com/t/terms)は、サービスが認める場合、事前の許可がある場合、または適用法で認められる場合などを除き、コンテンツのダウンロードや自動アクセスを制限している。**任意の公開動画 URL をサーバーが自動取得できる前提では設計しない。**

画面では URL を受けて動画の参照・再生に使い、解析には権利と利用条件を確認できる音源ファイルのアップロード、または許可を得た取得経路を使う構成が安全。これにより「URL だけで完結」を実現できる範囲は音源の利用許諾に依存する。公開サービス化する前に、取得方法と生成した譜面の公開・配布条件を確認する。

## 精度上の難所と評価方法

1. **楽器分離：** リードとバッキングが重なった曲、歪みが強い曲では 1 本のギターステムに複数パートが混ざり得る。UI で対象パートと区間を選べるようにする。
2. **音符推定：** 歪みによる倍音、ミュート、ベンド、速いピッキング、コードの同時発音で誤りが増える。元音・分離音・推定ノートを並べて比較する。
3. **運指：** 音高が正しくても演奏しにくい TAB になり得る。弦・フレットの編集を必須の機能として扱う。
4. **拍と音価：** 音声の秒単位のノート境界を譜面のリズムに変える工程を独立させる。最初は元音との同期表示を優先し、複雑な拍子の自動整形は段階的に改善する。

評価には正解の弦・フレット注釈を持つ [GuitarSet](https://github.com/marl/GuitarSet) と、ギター音声と TAB の対を持つ [GOAT](https://github.com/JackJamesLoth/GOAT-Dataset) を候補にする。ただしデータセットの演奏条件と実曲のミックスは違うため、利用許可を得た短い実曲区間でも比較する。指標は **音符の onset / offset / pitch F1、弦・フレット F1、演奏不能な割当の件数、ユーザーが修正した音の割合、処理時間**。同じ曲を各モデルで評価し、分離の有無による差も記録する。データセットの利用条件と学習済み重みのライセンスは導入前に個別確認する。

## 実装順

1. **小規模な検証：** 利用できるギター音源の 10〜30 秒で、Demucs + ギター専用モデル、Demucs + Basic Pitch、分離なしの 3 条件を比較する。
2. **TAB 化の検証：** ノートイベントから弦・フレットを割り当て、MusicXML を alphaTab で表示する。複数音のコードと標準チューニングを先に対応する。
3. **Web アプリ化：** URL 入力、許可済み音源の受け取り、ジョブ進捗、同期再生、TAB 修正・保存を追加する。
4. **精度改善：** 評価結果に応じて分離モデル、音符推定モデル、運指の重み、ベンドなどの奏法認識を追加する。

現段階ではライブラリの組合せについて実音源でのベンチマークは実施していない。上記の候補順位は公開資料からの設計判断であり、採用は短い検証で決める。
